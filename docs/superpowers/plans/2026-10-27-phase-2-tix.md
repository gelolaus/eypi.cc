# Phase 2 — Tix Rework Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** APC students register for events and keep tickets in Eypi; orgs pick an admission mode, manage one attendee pool, share private guest links, and run an offline-capable door.

**Architecture:** Extend `events` and `attendees` (migration `0011`) with a status machine in a pure module. Split `backend/src/routes/events.ts` into `backend/src/routes/events/*` by job. New attendee pages (`/tix/:slug` event page, `/tickets`, `/t/:token`) and org pages (builder, inbox, lottery, door) reuse the existing selection and scanner code.

**Tech Stack:** Vue 3, Hono, Turso/libSQL, existing `src/lib/tix/selection.ts`, `src/composables/useQrScanner.ts`, Google Wallet pass code, IndexedDB (native API, no library).

**Spec:** `docs/superpowers/specs/2026-10-27-eypi-speed-tix-analytics-design.md` §5. Phase 1 must be merged first (service worker, query cache, AppImage, PublicShell).

## Global Constraints

- **No ticket emails.** Guests get `eypi.cc/t/<token>` only; orgs copy or export it.
- Admission modes exactly: `fcfs`, `lottery`, `approval`, `import`. Statuses exactly: `pending`, `entered`, `waitlisted`, `confirmed`, `declined`, `cancelled`. Event status: `draft`, `published`, `closed`, `cancelled`. Visibility: `public`, `unlisted`.
- Up to 5 questions per event; types `text`, `choice`, `checkbox`. Description ≤ 4000 chars, Markdown sanitized with the existing `marked` + DOMPurify path.
- Guest token: 24 random bytes base64url; store only sha256 hex in `attendees.guest_token_hash`. Guest endpoint rate limit 30 per 10 min per IP.
- Check-in only for `confirmed`. `check_ins` rows only `checked_in` / `checked_out` from now on.
- All new and moved routes return `{ error: { code, message, fields? } }` via `backend/src/lib/errors.ts`.
- Flat org model: any activated member of the event's org manages it.
- Migration additive only (`UPDATE … WHERE` backfills allowed). `event_csv_rows` stays.
- Every task TDD; `npm run typecheck`, `npm test`, `npm run lint` green. Commits in owner style, **no co-author or tool trailers**, on `main`.

## Review Focus

- Two people register for the last FCFS seat at the same moment: exactly one is `confirmed`, the other `waitlisted` (or 409 `event_full` when waitlist is off) (Task 3 test `last seat race`).
- Registering twice for the same event returns the existing ticket, never a second row (Task 3 test `register is idempotent per user`).
- The same QR scanned on two offline door phones syncs as one check-in and one reported conflict (Task 8 test `two devices same attendee`).
- A rotated guest link stops working immediately; a cancelled guest ticket returns 404 (Task 7 tests).
- Registration before `registration_opens_at`, after `registration_closes_at`, on a `draft`/`closed`/`cancelled` event, or on an `import`-mode event is refused with a clear code (Task 3 test `refuses outside the window`).
